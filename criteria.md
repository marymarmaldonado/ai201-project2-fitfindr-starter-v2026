# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:** I chose 4 out of 5 because the agent uses model-generated responses, so I do not expect every run to behave exactly the same. I still want it to successfully complete the full process most of the time.

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:** I chose 5 out of 5 because if there are no listings, there is no item that can be passed to the next tool. This is something the agent should handle consistently instead of trying to continue with missing information.

## 3. Something about state

Given a query that returns at least one listing, the item stored as `selected_item` in the session is the same item passed into `suggest_outfit` — in 5 of 5 tries.
<!-- YOU WRITE THIS ONE.

     How would you know that the item your search found is the same item the
     next tool received? Name something countable or observable.

     This is the criterion people find hardest, because state failure doesn't
     look like state failure — it looks like a tool problem. Something that
     compares session["selected_item"] against what actually reached
     suggest_outfit is the shape you're after. -->



**Why this target:** I chose 5 out of 5 because the session is supposed to carry the result from one tool to the next automatically. If a different item gets passed into `suggest_outfit`, then the state is not working correctly.

## 4. Something about the fit card

<!-- YOU WRITE THIS ONE.

Given a successful run, the fit card mentions the selected item, its price, its platform, and gives a clear description of the outfit or overall vibe — in at least 4 of 5 tries.


**Why this target:** I chose 4 out of 5 because the fit card is generated by the model, so the wording can change between runs. I care more about it consistently including the important information than having the exact same wording every time.
